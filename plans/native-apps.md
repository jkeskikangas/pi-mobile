# Native apps (iOS first, Android later) — Implementation plan

**Why:** voice mode is built for eyes-busy use (running, cycling, driving, cooking), and the web app cannot keep the microphone with the iPhone screen locked, and cannot be started hands-free. A native app can. See `docs/voice.md` → Platform limits.
**Read first:** `docs/voice.md` (voice design and behaviour), `docs/voice-best-practices.md` (each practice and its evidence), `docs/native-research.md` (native platform research with sources, **[verify]** marks), `docs/design-principles.md` and `docs/ui.md` (UI rules), `README.md` (product). The web implementation that the native app must match is `web/voice.js` and `web/voice-core.js`; voices are defined in `src/voice/personas.ts`.
**Last checked against the code:** 2026-10-10 (after 0.1.4: voice personas, voice mode in light and dark, hold the circle to talk, voice settings in a sheet).
**Audience:** an agent with no other context. Every step names the files, the behaviour, and how to check it.

Each step ends green: the step's own checks pass, `npm test` and `npm run typecheck` still pass, and it is committed on its own (repo convention: plain-English subject, body explaining why). Steps marked **[device]** need a real iPhone; everything else runs on this Mac (Xcode 26.6, XcodeGen installed, iOS simulator runtime present).

**Coordination:** other agents edit `src/hub.ts`, `src/index.ts`, `web/app.js` and `web/app.css`. Keep edits there small and anchored; commit only your own hunks (`git add -p`, or stage from `HEAD` plus your hunks).

## 0. Decisions (made; do not reopen without new evidence)

| # | Decision | Why |
|---|---|---|
| D1 | **One native iOS app** in Swift/SwiftUI that embeds the existing web UI in a `WKWebView` and does natively only what the web cannot: QR pairing, voice mode, dictation audio, hands-free start, Live Activity, later push. | One app for the user; the web UI is already complete and keeps evolving (`docs/ui.md`); duplicating it would fork the product. |
| D2 | **Voice mode runs fully native** (audio session, WebRTC, realtime protocol, pi client, voice screen). The `WKWebView` is not used during voice mode. | WebKit suspends web views and their capture in the background; voice must survive a locked screen (`docs/native-research.md` §11). |
| D3 | **Decision logic is shared, not ported:** the app evaluates `web/voice-core.js` in JavaScriptCore (`JSContext`) and calls `PiVoiceCore.parseCommand`, `answerFor`, `requestNames`, `isDestructive`, `isBackchannel`, `isEcho`, `isSignificant`, `speakPrompt`, `incomplete`, `chunks`, `HELP`, `EARCONS`. It loads the file from the paired hub (`GET /voice-core.js`), falling back to a copy bundled at build time. | One source of truth for safety-relevant decisions (destructive confirmations, undo window, echo). The hub version always matches the hub. |
| D4 | **WebRTC via `stasel/WebRTC` (SPM)**, audio plus the `oai-events` data channel, same SDP flow as the web: the app sends its offer through the sealed RPC (`voiceSession`), the computer posts it to OpenAI with the user's ChatGPT sign-in or API key, the app gets the answer. **No WebSocket transport**, no OpenAI credentials on the phone. | Matches the web; WebRTC's audio unit gives Apple's echo cancellation; the ChatGPT-sign-in path is WebRTC only (`docs/native-research.md` §2). |
| D5 | **Audio session:** `RTCAudioSession.useManualAudio = true`; category `.playAndRecord`, mode `.voiceChat`, options `[.allowBluetoothHFP, .defaultToSpeaker]`; activate in the foreground, then `isAudioEnabled = true`; `UIBackgroundModes: audio`. | Background capture and hardware AEC (§1). |
| D6 | **Crypto: `swift-sodium`** `SecretBox` (XSalsa20-Poly1305), wire format `base64url(nonce(24) ‖ box)`, verified against vectors produced by tweetnacl-js. | Must interoperate with `src/crypto.ts` byte for byte (§8). |
| D7 | **Hands-free start:** `StartVoiceIntent: AudioRecordingIntent, ForegroundContinuableIntent` (`openAppWhenRun = false`): start the Live Activity, then the mic; if the Live Activity cannot start headless, `requestToContinueInForeground()` and retry. Exposed through App Shortcuts (Siri phrase), a `ControlWidget` (Control Center, Lock Screen, Action button) and Shortcuts. | Apple requires a Live Activity for background recording; headless start while locked is unreliable, the fallback makes it work (§3). |
| D8 | **No CallKit.** AirPods mute through `AVAudioApplication` input mute. | Apple rejects CallKit for non-calls (§6). |
| D9 | **Push is a later step** (Step 9), via APNs sent by the hub with the user's own `.p8` key, payload end-to-end encrypted and decrypted by a Notification Service Extension. | Background audio covers the live session; APNs keys are per developer team (§7). |
| D10 | **Project generated by XcodeGen** from `native/ios/project.yml`; the `.xcodeproj` is not committed. | Text-only project files are reviewable and agent-editable. |
| D11 | **Distribution:** paid developer account and TestFlight for anything beyond the developer's own device. Free 7-day provisioning works for development (no push). | §9. |
| D12 | **Android later** (Step 10), Kotlin, same architecture: WebView for the UI, native voice in a `microphone` foreground service. No Android Auto UI. | §10. |

Non-goals: CarPlay (not essential; in the car the phone's audio routes through the car and the Live Activity shows on CarPlay without any CarPlay code); rewriting the web UI natively; a WebSocket realtime path; CallKit; an App Store release in this plan; sharing Swift and Kotlin code.

## 1. Protocol reference (what the app speaks)

All of it exists today; the web app (`web/app.js`, `web/voice.js`) is the reference client and `test/phone.ts` a minimal one in TypeScript.

**Envelope** (`src/crypto.ts`): `seal(key, value) = base64url(nonce24 ‖ secretbox(JSON(value), nonce, key))`; base64url without padding. Every request payload includes `t` (client time, ms); the hub rejects payloads outside ±10 min of its clock and replayed nonces (`ReplayGuard`).

**Pairing** (single use, 10 min): the QR encodes `<origin>/#p=<pairingId>.<base64url key>` (`Hub.createPairing`). The app `POST <origin>/api/pair` with `{ p: pairingId, b: seal(pairKey, { t, name }) }` and gets `{ b: seal(pairKey, { d, k, role, host }) }`: device id `d`, device key `k` (base64url, 32 bytes), `role` (always `control`), `host` (machine name). Store `{ origin, d, k, role, host }` in the Keychain. 410 = expired/used, 401 = bad.

**RPC:** `POST <origin>/api/rpc` with `{ d, b: seal(k, { t, m, p }) }` → `{ b: seal(k, { r }) }` or `{ b: seal(k, { e: message }) }`; HTTP 401 = device revoked/unknown (unpair). Hub methods (`Hub.deviceCall`): `hub` (→ `{ hubId, host, seq, agents: AgentInfo[], device, pushKey, pushOn }`), `focus { client, agent }`, `push`, `devices`, `revoke { ids }`, `pair`, and `agent { agent, m, p }` which forwards method `m` to that pi session (`Bridge.handle`). Agent methods used by the app:

| Method | Params → result | Used for |
|---|---|---|
| `snapshot` | `{ limit, before? }` → `{ n, info, items, start, total, streaming, tools, prompts }` | prompts open at start |
| `send` | `{ text, images?, mode: "steer"\|"followUp" }` → `{ delivered: "prompt"\|"steer"\|"followUp"\|"command" }` | `ask_pi` |
| `answer` | `{ id, value }` | dialogs |
| `abort` | `{}` | stop |
| `voiceStatus` | `{}` → `{ speech, status, elapsedMs, tools, prompts }` | "what's it doing?" |
| `brief` | `{ mode: "eyes-busy"\|"glance" }` → `{ speech, more, report, by }` | after each run |
| `details` | `{ topic, mode }` → `{ speech }` | `pi_details` |
| `voiceSession` | `{ sdp, mode, persona? }` → `{ sdp, model, provider }` | realtime call; error text containing `realtime unavailable` → basic voice |
| `voiceState` | `{ on, mode }` | every 60 s while voice mode is on (expires after 150 s) |
| `transcribe` | `{ audio: base64, mime, distill?, draft? }` → `{ raw, text, editor, unclear, provider, by }` | dictation, basic voice |
| `distill` | `{ raw, draft? }` → `{ text, editor, unclear, by }` | basic voice |
| `speak` | `{ text, persona? }` → `{ audio: base64, mime }` or error `tts unavailable` | basic voice output, voice samples |
| `voices` | `{}` → `{ personas: [{ id, name, blurb, rate, phone: { prefer, pitch } }], sample }` | voice picker; `sample` = the computer can speak a sample |
| `learn` | `{ distilled, sent }` | dictation corrections |

**Events:** `GET <origin>/api/stream?d=<d>&b=<seal(k, { t, hub, since, focus })>` is Server-Sent Events. Each `data:` line is `seal(k, HubEvent[])` (a batch); `: ping` comments arrive every 15 s (reconnect if nothing for 40 s). The first event is `{ type: "hello", hubId, seq, resync, client }`: keep `hubId` and the highest `seq` for resumption, call `focus { client, agent }` to receive the detailed events of one session. Every client gets `info`, `gone`, `prompt`, `prompt_end` for all sessions; the focused session also gets `item`, `stream*`, `tool_start|update|end`, `notice`, `reset` (`src/protocol.ts` `AgentEvent`, `src/hub.ts` `GLOBAL_EVENTS`).

`persona` is the phone's pick (`marin`, `cedar`, `coral`, `ash`); omitted, the computer's config or Marin applies. It changes only how pi sounds, never what it says.

**Machines** (`plans/multi-machine.md` v2, shipping before this app): the phone holds the list of machines and talks to each directly; no machine relays for another. The app does what `web/fleet.js` does:
- it keeps `[{ id, name, origin, d, k }]` in the Keychain, migrating the single paired device;
- it opens one sealed RPC and event stream per machine;
- sessions are keyed `machine/agent`;
- a machine that can't be reached shows as offline.

Machines are added by a trusted machine (`/remote add box`). The offer arrives as a `machine_offer` event (or a push) and the app asks "Add box?". Add a computer (scan or paste) is the fallback. With APNs (Step 9), every machine sends its own notifications. Voice follows `plans/multi-machine.md` step 7:
- `PiVoiceCore.matchSession` for switching;
- one speech machine per voice mode;
- the machine named only when there are several;
- a dropped machine announced once.

**Realtime events** handled by the web voice mode (port these exactly, `web/voice.js` `onRealtime`): `session.updated`, `input_audio_buffer.speech_started|speech_stopped`, `conversation.item.input_audio_transcription.delta|completed`, `response.created|done`, `output_audio_buffer.started|stopped|cleared`, `response.output_audio_transcript.delta|done`, `response.function_call_arguments.done`, `error`. Sent: `conversation.item.create` (message or `function_call_output`), `response.create`, `response.cancel` (only while a response is active), `output_audio_buffer.clear`, `input_audio_buffer.commit|clear`, `session.update` (turn detection off while pi speaks, restored after).

## 3. Step 1 — Hub support (TypeScript, small)

1. `src/hub.ts` `deviceCall("hub")`: add `protocol: PROTOCOL` and `features: ["voice", "voiceSession", "speak", "voices", "learn", "machines"]` so the app can refuse an incompatible hub with a clear message.
2. `test/vectors.ts` (new, run by `npm run vectors`): writes `native/fixtures/crypto-vectors.json` with deterministic cases: fixed 32-byte key and 24-byte nonce → sealed string for several JSON values (ASCII, emoji, 100 KB), plus three invalid inputs (tampered byte, short input, wrong key) that must fail. Add a `sealWithNonce(key, nonce, value)` helper next to `seal` in `src/crypto.ts` (used only by the vectors and tests).
3. `test/crypto.test.ts`: a test that `open(sealWithNonce(...))` round-trips and that the committed vectors file matches regeneration.

**Check:** `npm test`, `npm run typecheck`; `git diff` shows only these hunks in `src/hub.ts`.

## 4. Step 2 — Project skeleton and Core

1. `native/ios/project.yml`: iOS 18.0 deployment target (iOS 26 SDK), Swift 6, targets `Pi` (app), `PiWidgets` (widget extension), `PiTests`, `PiIntegrationTests`; packages `jedisct1/swift-sodium` and `stasel/WebRTC` (pin exact versions; record them in `native/ios/README.md`). Bundle id prefix from a build setting `PI_BUNDLE_PREFIX` (default `dev.pimobile`) so a developer can set their own team.
2. Info.plist keys: `UIBackgroundModes: [audio]`; `NSMicrophoneUsageDescription` ("pi listens while voice mode or dictation is on"); `NSCameraUsageDescription` ("scan the pairing code"); `NSLocalNetworkUsageDescription` ("reach pi on your computer"); `NSSupportsLiveActivities: YES`; ATS: `NSAllowsLocalNetworking: YES` plus `NSAllowsArbitraryLoads: YES` with a comment that every payload is end-to-end encrypted (hubs are reached over LAN or Tailscale IPs on plain HTTP). **[verify]** whether `NSAllowsLocalNetworking` alone covers Tailscale `100.x` addresses; if it does, drop `NSAllowsArbitraryLoads`.
3. `Core/Envelope.swift`: `seal(key:value:) -> String`, `open<T: Decodable>(key:sealed:) -> T?`, base64url helpers. JSON with `JSONSerialization`/`Codable`; values sent are `[String: Any]` encoded through `JSONSerialization` to keep key order irrelevant.
4. `Core/HubClient.swift` (actor): `pair(link:name:) async throws -> Device`, `rpc(_ m: String, _ p: [String: Any]) async throws -> Any`, `agent(_ agent: String, _ m: String, _ p:) async throws -> Any`, `events(since:) -> AsyncThrowingStream<HubEvent, Error>` (URLSession `bytes(for:)`, line-based SSE parser, batches decoded with `open`, reconnect with backoff 0.5–8 s, stall detection 40 s, `hello` handling and re-`focus`). Errors: `.unauthorized` (401, the app unpairs), `.remote(String)`, `.network`.
5. `Core/Keychain.swift`: store the device (`kSecClassGenericPassword`, accessible `AfterFirstUnlock` so voice keeps working when the phone locks mid-session), shared access group (for the widget extension and, later, the notification extension).
6. `PiTests`: crypto vectors from `native/fixtures/crypto-vectors.json` (bundle it as a test resource); SSE parser (chunk boundaries, comments, multi-line); HubClient request shapes with a `URLProtocol` stub.

**Check:** `cd native/ios && xcodegen && xcodebuild test -scheme Pi -destination 'platform=iOS Simulator,name=iPhone 16'` passes.

## 5. Step 3 — Pairing and the web shell

1. First launch shows `PairingView`: "Scan the code from `/remote` on your computer" with a VisionKit `DataScannerViewController` (QR only) and a "Paste link" fallback. Parse `<origin>/#p=<id>.<key>`, call `pair`, store, then show the shell. The device name sent is "iPhone · pi app".
2. `Shell/WebShell.swift`: a `WKWebView` loading `<origin>/`. Before any page script runs, a `WKUserScript` (`.atDocumentStart`) sets `localStorage["pi-mobile-device"] = JSON({ d, k, role, host })` (the key and shape `web/app.js` reads, `DEVICE_KEY`) and `window.PiNative = { version: 1 }`. The web app therefore starts already paired with the same device.
3. Voice preferences are shared with the web UI, which owns their keys: `pi-mobile-voice-persona` (voice), `pi-mobile-voice-attention` (`eyes-busy`|`glance`), `pi-mobile-voice-turns` (`open`|`tap` = push to talk), plus `pi-mobile-voice-uses`/`-intro` (hint fading). The app keeps them in `UserDefaults`, writes them into `localStorage` in the same document-start script, and the web posts `{ type: "prefs", key, value }` when one changes, so a voice picked in the web menu is the voice of the native voice mode.
4. Message handler `piNative` (`WKScriptMessageHandlerWithReply`) for the calls in Step 4 and 6. Unpairing in the web UI (`unpaired()` clears localStorage) must also clear the Keychain: the web posts `{ type: "unpaired" }`.
5. Pull-to-refresh is off; `allowsInlineMediaPlayback = true`; the web view's background matches `--bg` to avoid flashes; safe areas are handled by the page (`viewport-fit=cover`).
6. `PiIntegrationTests` (simulator, local network): start the fixture hub with `npm run ui` (it prints a pairing link on `127.0.0.1:7979`), pair through `HubClient`, call `hub`, open the event stream, see `info` events, answer a prompt (`ask` on the fixture's stdin raises one). Document the run in `native/ios/README.md`.

**Check:** integration tests pass in the simulator; manually, the app pairs by scanning and shows the full web UI.

## 6. Step 4 — Web hooks for the native shell (TypeScript/JS, small)

In `web/voice.js` only (plus one line in `web/app.js` if needed), when `window.PiNative` exists:

1. The header voice button calls `webkit.messageHandlers.piNative.postMessage({ type: "voice.start", agent: S.current })` instead of opening the web voice screen. The secure-context check is skipped (the native app has the microphone).
2. Dictation: `startDictation`/`finishDictation` ask the native side to record (`{ type: "dictation.start" }`, `{ type: "dictation.stop" }`, `{ type: "dictation.cancel" }`); the reply of `dictation.stop` is `{ audio: base64, mime: "audio/mp4" }`; the rest of the existing flow (transcribe, raw/undo chips, `learn`) is unchanged. The recorder strip's waveform reads levels pushed by the native side (`window.PiNative.level(x)`).
3. The menu hides "Notify me" (Web Push does not exist in `WKWebView`) until Step 9 replaces it.
4. The menu's Voice row (`PiVoice.sheet`, the voice picker) stays in the web; it posts `prefs` on a pick. Its samples play in the web view (`speak`, else `speechSynthesis`).
5. When the native voice screen closes, the web reloads the focused session (`loadCurrent()`) so the transcript catches up.

**Check:** `npm test`; the web app in a normal browser behaves exactly as before (no `PiNative`); in the app, the voice button opens the native screen and dictation works over plain HTTP.

## 7. Step 5 — Voice engine (the core of the app)

Port `web/voice.js` `class VoiceMode` to `Voice/VoiceEngine.swift` (an `@MainActor` observable model) **behaviour for behaviour**. Decisions that `voice.js` delegates to `PiVoiceCore` go through `Voice/VoiceCore.swift`, which evaluates the hub's `voice-core.js` in a `JSContext` and exposes typed Swift wrappers (`parseCommand(_:) -> Command?`, `answerFor(prompt:text:) -> Answer`, `requestNames(prompt:said:)`, `isEcho`, `isBackchannel`, `isDestructive`, `isSignificant`, `speakPrompt(_:page:)`, `incomplete(_:)`, `chunks(_:)`, `help`, `earcons`). Do not reimplement those in Swift; the spoken settings commands (`PiVoiceCore.SETTINGS`: push to talk, open mic, eyes free, I can glance) also come from `parseCommand`.

The parts to port, with their web counterparts:

| Web (`web/voice.js`) | Native | Notes |
|---|---|---|
| `open`, `close`, `restart`, `heartbeat` | `start(agent:)`, `stop()` | `voiceState` every 60 s; `voiceState {on:false}` on stop |
| `startRealtime`, `stopRealtime`, `realtimeLost`, `rt`, `inject`, `respond` | `RealtimeClient` + engine | offer → `voiceSession`; data channel `oai-events`; first `inject` is the "[PI] Voice mode started…" context |
| `onRealtime` | `handle(event:)` | every case, including live captions and the session.updated capture of `serverTurns` |
| `clientTurns`, `clientVadFrame`, `duck`, `unduck`, `hardInterrupt` | same names | while pi speaks: `session.update` turn detection `null`, own VAD on mic level (use `PiVoiceCore.Vad` through JSContext or a Swift port with the same constants), duck = remote track volume 0.2 (`RTCAudioTrack` volume or the audio session output gain [verify]), `BARGE_MS = 800`, `SHORT_TURN_MS = 1300`, short sounds committed and judged by transcript |
| `tool` (`ask_pi`, `answer_question`, `stop_pi`, `pi_status`, `pi_details`, `switch_session`, `remain_silent`), `runCall` | `tools.swift` | same outputs; `ask_pi` cuts the response audio (`output_audio_buffer.clear`); `switch_session` through `PiVoiceCore.matchSession` |
| `speechAgent`, `onMachine` (from `plans/multi-machine.md` step 7) | same | one speech machine per voice mode; `machine_down`/`machine_up` announced once; speech machine lost → the realtime call stays up (its audio goes straight to OpenAI) and the next speech call (`speak`, `voices`, `transcribe`, a redial's `voiceSession`) re-picks another capable machine, once; basic voice only when the call itself drops (decided 2026-10-11) |
| `onEvent`, `settled`, `ask`, `tell`, `follow`, `tick` | `handle(hubEvent:)` | brief after a run, prompts read out, other sessions announced, significant tool failures, working tick every 6 s |
| `startGrace`, `finishGrace`, `cancelGrace`, `dropGrace`, `namedEarlier`, `rememberHeard`, `cancelsGrace` | same | the undo window (`GRACE_MS = 4000`) and echo marking |
| `pressStart`, `pressEnd(held)`, `toggleTalk`, `tap` | same names | push to talk on the circle: a press starts a turn, letting go after `HOLD_MS = 350` ends it, a shorter press toggles (tap to start, tap to stop); in open mic a tap interrupts or unmutes |
| `applySetting`, `settingsSheet`, `setPersona` | same names | a spoken setting changes it and pi says only "Okay."; a new voice redials the realtime call with `persona` and injects "This is <name>." |
| `basic(error)` | same | note "Using basic voice. Details in voice settings." for 8 s; the reason is kept for the settings sheet |
| `startCascade`, `onFrame`, `endTurn`, `handleUtterance`, `speak`, `speakLocal`, `silence` | `BasicVoice.swift` | basic voice when `voiceSession` fails: mic via `AVAudioEngine` input tap (16 kHz mono PCM, WAV encode), `transcribe`/`distill`/`send`, speech via `speak` with `persona` (hub TTS) else `AVSpeechSynthesizer`: pick a voice whose name matches the persona's `phone.prefer`, apply its `phone.pitch` and `rate` |
| `EARCONS`, `earcon()` | `Earcons.swift` | render the tone steps from `PiVoiceCore.EARCONS` to PCM buffers once; play with `AVAudioPlayerNode` on an `AVAudioEngine` that shares the session [verify it mixes with WebRTC's VPIO output] |

`AudioSessionController.swift`: owns `RTCAudioSession` configuration (D5), interruptions (pause on `.began`; on `.ended` resume only with `.shouldResume`, else state `paused` with "Tap to resume"), route changes (update the route label; never stop on AirPods disconnect, switch to speaker), and `AVAudioApplication` input mute (D8: observe `inputMuteStateChangeNotification`, call `setInputMuted`, mirror to `track.isEnabled`; the engine's `muted` state follows it). On network change (`NWPathMonitor`): reopen the event stream and do an ICE restart (new offer → `voiceSession` is acceptable if ICE restart is not supported by the endpoint [verify]).

`Levels.swift`: poll `RTCPeerConnection.statistics` every 100 ms for `media-source` (mic) and `inbound-rtp` (pi) `audioLevel`; publish a smoothed 0–1 level for the orb, the Live Activity and the dictation strip.

**Tests (`PiTests`, no network):** a `FakeRealtime` (records sent events, lets the test emit server events) and a `FakeHub` (records RPCs, emits hub events) drive `VoiceEngine` through the scenarios that `test/e2e/turns.mjs` and `docs/voice.md` → Verification cover:
- two machines: switching to a session on the other machine keeps the call; its `machine_down` is announced once; speech calls go to the speech machine and session calls to the session's machine;
- question → `ask_pi` with the transcript, response audio cleared, state `working`, `brief` after `info` idle → injected `[PI] pi finished…` and `response.create`;
- backchannel while speaking: duck, no `response.cancel`, unduck after the transcript says "mm-hmm";
- interruption: duck, `hardInterrupt` after 800 ms voiced, commit and respond on end;
- destructive prompt + earlier "deploy the app to production" → grace → `answer {value:true}` after 4 s; "stop" within the window → `answer {value:false}`;
- bare "yeah" to a destructive prompt → refused; echo of pi's words → never counted;
- `voiceSession` error `realtime unavailable` → basic voice.
Use the real `voice-core.js` from `web/` in these tests (bundle it), so a change there that breaks the app shows up here.

**Check:** unit tests pass; in the simulator with the Mac's microphone, voice mode against a real pi (set up as in `docs/voice.md` → Verification) answers a question.

## 8. Step 6 — Voice screen (SwiftUI)

Mirror the web voice screen (`docs/design-principles.md` §4, `web/app.css` `.voice` block, `web/index.html` `#voice`); do not invent a new design.

- Follows the system light or dark appearance like the rest of the app; the orb keeps the vivid dark-palette state colours (`--d-*`) in both (`listening` blue/cyan, `thinking` violet, `working` amber/orange, `speaking` green/cyan, `asking` gold with a ring, `paused`/`connecting`/`offline` grey); labels and hints with the same copy as `voice.js` `LABEL`, `hint()`.
- `OrbView`: `TimelineView(.animation)` + `Canvas`, a blob that swells with the level (yours while listening, pi's while speaking), breathes while working; `accessibilityHidden(true)`; the state label is the accessibility element. Reduced motion (`@Environment(\.accessibilityReduceMotion)`): a still disc.
- The circle is one big button and the push-to-talk surface: hold while you talk, or tap to start and stop (`pressStart`/`pressEnd`); in open mic a tap interrupts or unmutes. Its accessibility label names the action; VoiceOver activation is a tap. While held it swells slightly and never overlaps the label.
- Header: the session name (opens the session switcher, a sheet listing `AgentInfo`s grouped Needs you / Working / Idle) and a settings button. Middle: captions ("You" and pi, live; pi's caption hidden while a question card shows it) and the question card with tap answers (destructive in red, undo-window countdown bar, Cancel / Do it now). Bottom: just two labelled 68–72 pt buttons, Mute and End (red).

## 11. Step 9 — Push notifications (optional, needs a paid account)

1. Hub (`src/apns.ts`, new; `src/store.ts`): APNs over `node:http2` with token auth (ES256 JWT from a `.p8`, `kid` = key id, `iss` = team id, refreshed every 30 min), `POST /3/device/<token>` to `api.push.apple.com` or the sandbox. Config: `apns: { keyFile, keyId, teamId, topic, sandbox }` in `config.json`, set through `/remote settings`.
2. RPC `push` accepts `{ apns: { token, sandbox } }` beside the Web Push subscription; `Hub.attention()` sends to both kinds.
3. Privacy: the alert payload carries only `{ aps: { alert: { title: "pi", body: "…" }, "mutable-content": 1 }, sealed: seal(deviceKey, { title, body, agent }) }`; a Notification Service Extension (new target `PiNotifications`) opens `sealed` with the device key from the shared Keychain and rewrites the title and body. Apple sees no session names or questions, matching Web Push today.
4. Tapping a notification opens the app on that session (`agent` in the payload); an urgent "asks" notification offers "Answer by voice" (starts `StartVoiceIntent` focused on that session).

**Check:** unit tests for the JWT and request shape (fake http2 server); **[device]** end to end.

## 14. Risks and open questions

- **Headless start while locked** may stay unreliable (§3): the fallback opens the app; document the real behaviour.
- **AirPods mute** for a non-CallKit `.voiceChat` WebRTC app is unverified (§6).
- **Earcons mixing with WebRTC output** and **ducking the remote track** need a device check; fallback for ducking: set the realtime model's output to silence by pausing the remote track and resuming (`RTCAudioTrack.isEnabled`) — loses the "quieter" cue but keeps the decision logic.
- **The ChatGPT-sign-in realtime endpoint** is undocumented and may change; the hub already falls back to basic voice, which the app supports.
- **ATS for plain-HTTP hubs:** confirm the minimal exception set before any TestFlight build; App Review may question `NSAllowsArbitraryLoads` (justify: end-to-end encryption, user-owned server).
- **App Review** for background audio: the mic is live only during a visible session with a Live Activity (guideline 2.5.4).
