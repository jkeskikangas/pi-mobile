# Voice: dictation at the desk, conversation on the move

Two different jobs, designed separately.

| | **Voice input** (desk) | **Voice mode** (phone, eyes and hands busy) |
|---|---|---|
| You | look at the screen, read everything | running, cycling, driving, cooking: cannot read or type |
| Speech is | a faster keyboard | the only channel, both ways |
| Output | a *written* prompt in the editor, for you to check | spoken words, as few as possible, plus the full written transcript for later |
| Failure to avoid | a verbatim transcript full of "um, no wait, the other file" | a model reading markdown, paths and diffs aloud |

## What the state of the art does (October 2026)

Research notes with sources: [voice-research.md](voice-research.md).

- **Codex voice** (ChatGPT app, Codex CLI `/voice`) puts a thin realtime voice model (GPT-Live / `gpt-realtime`) in front of the coding agent. The voice model has two tools, `background_agent(prompt)` ("pass along the user's own words") and `remain_silent()`; agent output is injected as `[BACKEND] …`. Its prompt forbids reading code, diffs and tables, and asks for progress updates only when "genuinely useful". It is a good conversational shell, but it assumes you can glance at the screen for anything detailed.
- **Claude Code `/voice`** is dictation only: hold-space push-to-talk, Deepgram Nova-3 streaming STT with key terms (project name, branch words, recent files), a dimmed live transcript inserted at the cursor, auto-stop on silence. The text is verbatim.
- **Dictation tools** (Wispr Flow, Superwhisper, Aqua) add an LLM cleanup pass: backtrack ("scratch that", restating), filler removal, list formatting, identifier recognition from the open editor, spoken file names as `@file` mentions.

None of them does both jobs well, and none treats "I am driving" as its own interaction design.

## Design principles

### Voice input

1. **Intent, not transcript.** Speech is high-bandwidth but redundant and ambiguous. The output is the prompt you would have typed: self-corrections applied, filler and restarts gone, the request ordered (goal, constraints, steps), every concrete detail you said kept.
2. **Ground the words in the workspace.** Spoken identifiers are matched to real ones: `get user by id` → `getUserById`, "orthodotts" → `auth.ts`. The vocabulary comes from the repo (tracked file names, the current branch) and the session (identifiers and paths in recent messages). The same vocabulary biases the recogniser.
3. **Surface ambiguity, never paper over it.** When something you said has two readings, the distilled prompt keeps your words and adds a short `(unclear: …)` note, instead of silently picking one.
4. **You stay the editor.** The distilled prompt lands in the editor, not in the model. One key swaps to the raw transcript, one key cancels and restores what you had typed.
5. **Stream what you say while you say it.** A live (dim) transcript and level meter show the mic is hearing you. Distillation runs once, when you stop. On the phone, hold the mic and let go (walkie-talkie), or tap to start and stop; a waveform shows it hears you.
6. **Edit by voice.** With text already in the editor, dictating "make that a list", "drop the second point" or "change X to Y" edits it instead of appending the words.
7. **Learn from corrections.** When you fix a distilled dictation before sending it, the replaced names ("get user" → `fetchUser`) go into a personal dictionary (`voice-dictionary.json` in the state dir) that biases recognition and distillation from then on.
8. **Free and private by default.** On a Mac the recogniser is Apple's on-device SpeechAnalyzer (macOS 26): no account, no audio leaves the machine, about 2% WER on clean speech, contextual-string biasing. An OpenAI API key (`OPENAI_API_KEY`) switches to `gpt-4o-transcribe` where SpeechAnalyzer is unavailable. Distillation uses a model you already have in pi.

### Voice mode

1. **Talk about intent, not code.** Nobody discusses variable names on a run. Voice conversations are about behaviour, architecture, decisions, trade-offs, risks and what is left. The voice never says identifiers, file names, paths, commands, test names or tool names unless asked; it names parts of the system by what they are ("the login flow", "the phone app"). The agent is told the same, and maps what the user describes onto the code itself.
2. **Tool activity is not news.** Reads, searches, edits and routine commands stay silent, and routine failures the agent recovers from are its own business. Only *significant* actions reach the ear: anything touching production systems or data, deployments, shared history (push, force, reset), deletions, external services or money. When one fails, the phone plays a failure tone and the voice says what kind of action failed, while pi keeps working.
3. **Two output channels for every run.** The agent writes as usual: the transcript keeps the full written answer for when you're back at a screen. What you *hear* is a spoken brief written for the ear: the outcome first, one idea per sentence, numbers rounded, no code, no symbols, no markdown. The report behind it is organised by area of the system and significant actions, not by file or tool.
4. **Say less, offer more.** A brief ends, when there is more, with one offer at the same level ("want to hear why the tests still fail?"). Details are answered on request at the level of behaviour; file names only when you ask "which files".
5. **Sounds for state, words for news.** Short earcons mark listening, heard-you, working (a soft tick every few seconds), needs-you, done and failed. Speech is reserved for things that change what you do next. "Status?" gets a one-sentence answer at any time from local state, without waking the agent: how long pi has worked, what kind of thing it is doing ("running the tests", never which file), and the last thing it said it was doing.
6. **Commands are instant.** "Stop", "stop pi", "repeat", "status", "shorter", "go on", "yes/no", "option two" are recognised locally with no model round trip. Interrupting the voice never stops pi: "stop", "cancel", "shush" stop the voice; only "stop pi", "cancel that", "stop the work" or "abort" stop pi's work (`web/voice-core.js` `stopPi`, the same words as the terminal's `voice-session.ts`).
7. **Questions are answerable by voice.** Any extension dialog (`confirm`, `select`, `input`) that pi raises is read out (two options at a time) and answered by voice. Permission gates are covered too. A question from another session is announced, and "switch to …" moves there.
8. **Destructive actions need an explicit spoken confirmation that names the action** ("push three commits to main? say *yes, push*"). A plain "yeah" from a noisy street is not consent.
9. **Defer what needs eyes.** In eyes-busy contexts the agent is told the user cannot read: it avoids asking for visual review, and the voice says the diff is waiting at a screen.
10. **Barge-in is a first-class signal.** Speaking while pi talks stops the audio immediately (echo cancellation keeps the speaker from triggering it), and what you say next is a new turn.
11. **Turn-taking fits the context.** Open mic with semantic end-of-turn detection in the car or kitchen; tap-to-talk (a screen-sized target, or a headset button where the browser allows it) when it's noisy, windy or you're cycling. In basic voice a trailing "and…", "um" or "wait" keeps the floor open.
12. **The voice never knows; pi knows. Acknowledge lookups, not work.** The voice answers only from the conversation, pi's reports and voice controls; anything needing a tool, a file or current information goes to pi (issue #5), including questions that aren't about the code ("what's the weather in Dublin?"). A lookup (the weather, docs, what is in a file) gets one word, "Checking.", because that wait would otherwise be silent; work (change, fix, rename, run) gets no announcement at all: the voice calls pi silently and the working tick carries the wait. The phone enforces it: when the voice hands a request to pi, whatever it was about to say with it is cut, except that one word. Preferences you state ("be terser") stick until you change them. (Revised for lookups by `designs/voice-modalities.md`; the rule text is shared by both surfaces in `realtime.ts`.)
13. **Soft barge-in.** About half of the sounds that trip a voice detector while an assistant talks are backchannels, coughs or echo. When you make a sound over pi, its voice drops to 20% within ~200 ms; it stops only after ~800 ms of voiced speech (Hume's default) or when your words turn out to mean something ("stop", "no"). "Mm-hmm" and coughs leave pi talking. Nothing you say is dropped unheard: short sounds are transcribed and judged by their words. (The realtime server clears the assistant's audio on any speech regardless of `interrupt_response`, a known API bug, so while pi speaks the phone does turn-taking itself and hands it back to the server's semantic VAD when pi is silent.)
14. **Ask once, with an undo window.** pi's permission dialogs for irreversible actions normally need the action named ("yes, deploy"). But if *you* just asked for exactly that action and target, the phone (not the model) recognises it from what it heard you say, the voice says "Deploying to production, say stop to cancel", and the dialog is confirmed after four seconds unless you say stop or tap Cancel. One spoken sentence instead of being asked three times.
15. **pi's own voice is never consent.** Speech heard while pi was talking that repeats pi's words ("say yes, deploy to confirm") is marked as echo: it cannot answer a destructive question or count as an earlier request.
16. **Help is a question away.** "What can I say?" gets a two-sentence answer; first-time users get a one-sentence spoken intro and rotating example hints that disappear after a few sessions.

### Voice mode in the terminal (`/voice`)

The same voice at the desk, with headphones, while pi's full answers stay on screen. Design: `designs/voice-modalities.md`; same realtime model, ChatGPT sign-in and brief writer as the phone.

- **Start and stop:** `/voice` or alt+v (alt+shift+v on Windows and WSL, where alt+v pastes images). Stopping works while it is still connecting (alt+v, `/voice`, a lost call, a microphone error): whatever it had opened by then, or opens after, is closed. pi's shutdown or `/reload` stops it without starting anything new (an open draft's view is closed, no finishing check runs on the old session), waits for a start in progress to let go, and puts pi's own dialogs back; the reloaded voice mode answers them again. The status line shows the state at all times: `voice: listening`, `speaking`, `working`, plus `quiet` or `eyes-free` when a switch is on.
- **One output rule.** The voice says how it went and when you're needed, in one sentence; everything else is text. Spoken: the outcome of a request, pi's questions (extension dialogs raised while voice is on are read out and answerable aloud, irreversible ones only with the action named), and failed significant actions (the significance rules of `speech.ts`). Each answer's spoken sentence is shown above it in the transcript as a **said** line in the accent colour (a custom session entry, `pi-speech-said`: displayed and kept, never sent to the model). The sentence is written by the brief writer in `message_end`, before pi shows the answer as final, so the line lands above the answer; the voice is told to say exactly it. A slow model falls back to the answer's first sentence after 6 s.
- **Only timing adapts.** Speech waits until you stop typing (1.5 s without a key, `typing-gate.ts`). A question or failure plays its sound at once and is spoken at the next pause; the done sound comes with the speech. The working tick never plays while you type.
- **Two switches,** said ("go quiet", "I can't look", "normal") or set with `/voice quiet|eyes-free|normal`, persisted as `voiceSwitch`: **Quiet** speaks nothing (sounds still mark needs you, done, failed; anything the voice would have said to you directly is shown as a notification), **Eyes-free** gives longer briefs and tells the voice and pi you can't look.
- **Requests.** A complete spoken request goes to pi at once (steering when pi is busy). One that points at something to come ("rename it to the following", "use this:", a final "to" or "as") is **parked**: the words land in the editor after a `●` marker with a "Finish typing · Enter sends" hint, the voice says nothing, Enter or saying "send" sends one message (typed text verbatim, marker stripped), Esc turns it into plain text, and nothing is ever sent by itself: the model's `send_parked` sends only when the developer's latest words were "send". The marker is stripped only while something is parked (a line typed with a leading `● ` is the developer's own), and a request still parked when voice mode ends stays as plain text. Parking is decided locally (`park.ts`: trailing pointing words) as well as by the model's `park` tool, and `ask_pi` refuses to send such a request. "This"/"that" means the editor's text when there is any, otherwise the last thing pi showed; the voice gets a short `[PI] SCREEN` note when that changes.
- **Interrupting the voice never stops pi.** Speaking over the voice stops it at once; "stop" stops only the voice. "Stop pi", "cancel that" stop pi (`ctx.abort()`), or drop a parked request when pi is idle. The words decide, not the model: its `stop_pi` waits for the turn's transcript and acts only when that was itself "stop pi" or "cancel that" (already done locally; the call reports it), so a plain "Stop." never stops pi.
- **A monologue becomes a draft** (`monologue.ts`, `voice-draft.ts`; design: *In voice mode: recognising a monologue*). It is the same draft, continuous drafting, transcript on disk, finishing check and full-screen view as a long dictation (`draft-session.ts`, `drafting.ts`, `draft-view.ts`); only the voice talking back differs.
  - **Starting:** the voice model calls the `draft` tool when it recognises composing (describing a feature, listing requirements, reasoning about a design or a bug), told never to for a single request or question. Locally, continuous speech for more than 20 s (pauses under 2.5 s, no request handed to pi, the voice not heard to the end in between) starts one too: in testing the replies to a fast talker's turns were barged into before the model could call anything, so the backstop is what catches a monologue without pauses. Nothing said is lost: the turns since the conversation last moved on (a request or command handled, a tool answered, 10 s of quiet) are the draft's first words, and a turn still being spoken lands in it when its words arrive. A soft two-note tone (`draft` earcon) and the view mark it; the status line says `voice: drafting · "that's it" finishes`.
  - **While drafting** the voice is silent: `session.update` sets `turn_detection.create_response` (and `interrupt_response`) to false and restores the configured turn detection when the draft closes; the terminal already asks for every reply itself, so the session also asks for none while a draft is open, except the draft's own lines. pi's news (and its done sound) waits until the draft closes; question and failure sounds still play at once, and the working tick stops. "Stop pi", "go quiet" and the other voice controls still work.
  - **What the draft hears:** the realtime session's own transcription of each turn (`gpt-4o-mini-transcribe` in the configured or system language). It is already running, so it costs nothing more; it is turn-aligned with the commands, so "that's it" or "no, just answer that" are left out exactly; and each turn is transcribed on its own, so a long monologue can't degrade a stream. Apple's on-device recogniser (proven over 10-minute streams for dictation) was tried first, fed from a pre-roll of the voice-mode microphone: on the end-to-end description below it heard "three retries" as "free retries", "offline" as "a flying" and "pause" as "cause", while the realtime transcription was word-perfect on all 17 turns. The cost: the Hearing line shows each phrase when its pause ends (about a second late), not word by word. A turn that can't be transcribed is said so in the Hearing line ("say it again").
  - **Undo:** "no, just answer that" ("just answer it", "that's not a draft") closes the view without sending, turns replies back on, and hands what was said to the voice as the developer's request (it calls `ask_pi` with their words, or answers itself).
  - **Closing:** "that's it" (also as the last sentence of a longer turn), Enter, or "yes" to "Is that everything?", which the voice asks once, quietly (no sound), after 8 s without speech; "no" or more speech goes on drafting. Then the last update and the finishing check, then one spoken sentence (the fast model: "Got it: nineteen things, retry behavior, queue handling, upload feedback and documentation, and one question."; without it, the count and the sections) with the draft as text.
  - **Clarifying:** the voice asks the open questions one at a time (one worded as a statement is asked as "Open question: …"); each answer goes to the draft as a change by voice (`DraftSession.change`), which resolves the question and glows; "skip" leaves it open; "no more questions" stops. While the draft waits, anything said is a change ("drop the point about docs"). Turns said during the check wait for it.
  - **Sending:** "send it" or Enter sends the draft to pi (steering when busy), or to the other session when the voice is switched there (`herdr agent prompt`; the hint and status line say "to api @devbox"); "send it" while still talking finishes, checks and sends without questions. Esc or "put it in the editor" moves it to pi's editor. Quiet: the question and read-back are notifications and there are no spoken questions. If voice mode ends with a draft open, the draft is finished and stays for Enter or Esc.
- **Lines said exactly.** Every line the voice must say as written (the output rule's sentence, pi's questions, the draft's read-back and questions) goes with its `response.create` as that response's own instructions (`sayInstructions`: say exactly this, word for word, nothing before or after, no tools; the persona's delivery kept), besides the `[PI] SAY` item that keeps it in the conversation. Before, the voice sometimes paraphrased the line.
- **Transcription language.** The realtime session's input transcription gets `locale` from the config or else the system language (`systemLanguage()`: macOS `AppleLocale`, else `LC_ALL`/`LC_MESSAGES`/`LANG`): without it a one-word reply ("Green.") was transcribed as Japanese. The phone's session is unchanged (the configured locale only).
- **Questions are answered by the developer, never by the voice.** With more than one question open (this pi's and another session's), `answer_question` needs the question's id: the voice asks which. It is refused unless the developer has spoken (a committed turn) since the question was asked: in testing, the voice model once picked an option itself the moment pi's question arrived.
- **One voice, many sessions** (`herdr-targets.ts`). The voice always runs in this pi, where the headphones are; other sessions (other herdr panes here, and saved SSH machines) are reached through herdr's CLI: `herdr [--machine m] agent list|get|prompt|wait|read|send-keys`, run with `execFile` and an argument list, JSON parsed defensively. pi-mobile's machine link is not used. On when pi runs inside herdr (`HERDR_ENV=1`) and the `herdr` command works; otherwise the voice says once that other sessions aren't available.
  - **Switching:** "switch to api", "talk to the pi on devbox", "treat on devbox", "back to this one" (`switch_session`). Names resolve against the agent's name, its folder, workspace or tab label, and the machine's label (spoken "voice target" finds `voicetarget`); a kind word narrows it ("the claude in treat"); a pi wins over other agents when the rest is a tie. Equally good matches are ambiguous: the voice asks which, naming at most three. The status line shows the target: `voice → api @devbox: listening`.
  - **Requests** go there instead of this pi: `ask_pi` → `agent prompt`, then the request is followed in the background (`agent wait --until working|blocked` to see it start, then `--until idle --until done --until blocked` in 60 s chunks, up to 30 min). The answer is read from the session file for a pi on this computer (`agent_session.path`: the exact text, edits and commands, the same digest as this pi's runs), otherwise from its screen (`agent read --source recent-unwrapped --lines 200`: after the request's echo, without tool lines, timings, the editor and footer). The brief writer makes the one spoken sentence; this pi's transcript gets `→ api @devbox  the request`, then `said api @devbox  the sentence` with a compact copy of the answer (custom entries, `pi-speech-remote`, never sent to this pi's model). An answer from a session other than the current target is said with its name ("From api on devbox: …").
  - **Its questions:** a session waiting on a question (`blocked`) gets no prompt (herdr would refuse it anyway); its dialog is read from the screen and asked by voice. Only select and yes/no dialogs with a visible cursor (pi's `→`) are answered, with arrows and Enter (`agent send-keys`), and only after re-reading that the same question is still on its screen: the same text and herdr's `state_change_seq` unchanged (two dialogs in a row can read the same; one asked again is a new question). The arrows go first; Enter only once a fresh read shows the cursor on the chosen option. A dialog whose long options look wrapped (a line as wide as the screen, numbered options with an unnumbered line) needs the screen; anything else (free text) "needs the screen". Chained dialogs (select, then confirm) keep herdr's state `blocked`, so the screen is re-read every few seconds to notice the next question.
  - **Parked requests** stay in this editor ("Enter sends to api @devbox") and go there on Enter or "send" (design open question 3).
  - **"Anything need me?", "what's devbox doing?"** (`list_sessions`): one or two sentences by project, this session left out: "Two need you: api on devbox and web. Working: treat (two); finished: docs; two idle."
  - **Robustness:** every herdr call has a timeout; a prompt is never resent (a herdr timeout or `agent_prompt_stalled` does not prove nothing arrived: the voice says it may have arrived, and the request is followed anyway); a saved machine that fails is reported as unreachable ("devbox didn't answer", "devbox is unreachable right now; nothing was sent"); a session that ended is said once. "Stop pi" while switched sends Esc to that session if it is working; `pi_status` asks herdr. The voice model can't send a request again within two minutes of an unconfirmed delivery of it. A request sent while the previous one is still followed gets its own answer: an answer counts only once herdr's state counter moved past the request's (herdr's `agent wait` does not track turns), otherwise the voice says the session doesn't seem to have started on it. Prompt text goes verbatim: herdr 0.9.3 takes text starting with `-` as the text (`--` is not an end-of-options marker there; it would be sent as the text), and several lines arrive as one bracketed paste, then Enter. herdr commands still running (a 60 s `agent wait`) are killed when voice mode ends.
- **Turns and barge-in.** Headphones are assumed (no echo cancellation). Turn detection defaults to server VAD (700 ms of silence, about 1.5 s turns; semantic VAD sometimes waited 4–10 s) unless `turnDetection` is `semantic`. The server clears its own audio when you start speaking, even with `interrupt_response: false`, so the terminal takes that hard interruption: on `speech_started` it kills the player at once (a spare is kept warm), sends `response.cancel` only while a response is being generated (`response.created`…`done`, tracked apart from the model being heard, `output_audio_buffer.started`…`stopped`), and never sends `output_audio_buffer.clear`. The reply to a turn is requested at once but its audio is held until the transcript is judged (parking, "send", the switches, a cough), at most 1.2 s, so a parked request never gets a spoken reply and an ordinary one costs no extra latency.
- **Testing without speakers:** `PI_SPEECH_PLAYER=file:<wav>` records what would be heard on a wall-clock timeline (a barge-in cuts it like the real player), `none` plays nothing; `PI_SPEECH_MIC=file:<wav>` is the microphone (followed by silence when it ends); `PI_SPEECH_VOICE_LOG=<file>` writes the realtime events and decisions as JSON lines (mode 0600: it holds transcripts).

## Architecture

```
terminal (desk)                      phone (voice mode / composer mic)
 ffmpeg mic → PCM ─┐                  getUserMedia ──WebRTC──▶ OpenAI realtime (gpt-realtime via your Codex sign-in or an API key)
                   ▼                     │  data channel: transcripts, tool calls ↕
        STT (Apple on-device | OpenAI)   │  tool calls → sealed RPC → hub → bridge → pi
                   ▼                     │  pi events  → SSE → phone → injected as [PI] context
        distill (pi model) → editor      └─ fallback: MediaRecorder → bridge STT → pi → brief → speechSynthesis

terminal voice mode (/voice, headphones)
 ffmpeg mic 48 kHz → opusscript → werift ──WebRTC──▶ OpenAI realtime (same session, ChatGPT sign-in)
 ffmpeg player ◀─ opusscript ◀─ RTP ◀─┘   data channel: transcripts, tool calls → pi in this process
                                        pi events → brief → [PI] SAY, said line in the transcript
```

Everything the phone and pi exchange stays end-to-end encrypted through the hub. The realtime session is set up by the bridge (it holds the credentials): the phone sends its WebRTC offer through the sealed RPC, the bridge posts it to the realtime endpoint and returns the answer. Audio then flows directly between the phone and OpenAI; no OAuth token ever reaches the phone.

### Modules

The computer side lives in the `pi-speech` package (`packages/pi-speech/`, an npm workspace): its own pi extension for terminal dictation, and the library pi-mobile's bridge uses for the phone. pi-mobile depends on it and bundles it. Settings and the learned dictionary are in `~/.pi/agent/pi-speech/`, copied once from pi-mobile's `"voice"` settings. The phone side (`web/voice*.js`) stays in pi-mobile.

| File | Responsibility |
|---|---|
| `packages/pi-speech/src/vocab.ts` | Workspace vocabulary: tracked files, branch words, declared code symbols (`git grep`), names in recent session messages; spoken forms; trigram-indexed fuzzy matching of what was heard to real names. |
| `packages/pi-speech/src/distill.ts` | The intent-distillation prompt and its output parsing; heuristic fallback (fillers, "scratch that", near-exact names, flags mid-sentence corrections) when no model is reachable. |
| `packages/pi-speech/src/speech.ts` | Writing for the ear: run digest by area and significant action, the spoken-brief prompt, `speakable()`, activity descriptions, significance rules, the agent's voice note. |
| `packages/pi-speech/src/host.ts` | The bridge's voice requests: transcribe, distill, brief, details, realtime call setup, listening state. |
| `packages/pi-speech/src/stt.ts` | STT providers: Apple SpeechAnalyzer helper (compiled once into the state dir), OpenAI transcription; selection. OpenAI has no streaming over HTTP, so live it transcribes the recording in pieces of about a minute (`piecewiseLive`: cut at the first 0.7 s pause after 50 s, or at the quietest moment of the last 15 s at 75 s; near-silent pieces aren't sent; a failed piece is tried once more), each piece a settled segment: a long dictation drafts live and its transcript is on disk while you talk. |
| `packages/pi-speech/src/apple-stt.swift` | On-device recogniser: file or streaming stdin PCM, contextual strings; streams JSON lines with the unsettled words (`volatile`) and each settled segment (`final`, at pauses). Each read pass drains an autorelease pool (without it the helper grew 12-17 MB a minute). |
| `packages/pi-speech/src/mic.ts` | Microphone capture via ffmpeg (avfoundation / pulse / dshow, or a file played in real time) as 16 kHz PCM (48 kHz for voice mode) with a level meter. |
| `packages/pi-speech/src/model.ts` | Fast-model candidates the user has credentials for; one completion, skipping models that fail; one completion on the session's own model (the draft's finishing check). |
| `packages/pi-speech/src/realtime.ts` | Realtime session config (voice-layer instructions and tools, for the phone or the terminal: `surface`) and the SDP relay to OpenAI. |
| `packages/pi-speech/src/voice-mode.ts` | Terminal voice mode as a pi extension: `/voice`, alt+v, the status line, the said line, pi's events to the voice, dialogs answerable by voice, the parked-line input hook. Registered once even when pi-mobile and pi-speech both load. |
| `packages/pi-speech/src/voice-session.ts` | Terminal voice mode's logic without pi or devices (tested with a fake clock): realtime events (response active vs. model heard, barge-in, held replies), output routing and the switches, the typing gate, parking, local commands, the voice's tools, routing to another session when switched. |
| `packages/pi-speech/src/herdr-targets.ts` | One voice, many sessions: herdr's CLI behind an injectable runner, the fleet across this computer and saved machines, name resolution, following a request to its answer (session file or screen), dialogs on another screen answered with keys, "anything need me?". |
| `packages/pi-speech/src/rtc.ts` | The realtime call from Node: werift WebRTC, Opus in and out with opusscript (wasm), the `oai-events` data channel. No native build. |
| `packages/pi-speech/src/audio-io.ts` | Voice mode's microphone (48 kHz) and player (ffmpeg to AudioToolbox, elsewhere ffplay; a spare kept warm for barge-in; SIGKILL on close), or a file player for tests. |
| `packages/pi-speech/src/earcons.ts`, `park.ts`, `dialogs.ts`, `typing-gate.ts` | The phone's earcons as PCM (plus the terminal's `draft` tone); parking (pointing words, the marked editor line); dialogs by voice (answers, destructive confirmation, one full stop per sentence); the 1.5 s typing pause. |
| `packages/pi-speech/src/monologue.ts` | A monologue in voice mode (no pi, no devices; tested with a fake clock): the 20 s backstop and what was already said, the `draft` tool's start, `create_response` off and back, the draft commands ("that's it", "no, just answer that", "send it"), "is that everything?", the read-back sentence, the clarification loop. |
| `packages/pi-speech/src/voice-draft.ts` | The monologue's draft on screen: a `DraftSession` fed with the realtime transcription's turns, the finishing check, the read-back from the fast model, voice hints in the view. |

### Bridge requests added

| Request | Payload → result |
|---|---|
| `transcribe` | `{audio: base64, mime, distill?, draft?}` → `{raw, text, editor, unclear[], provider, by}` |
| `draftStart` | `{}` → a draft view: `{id, version, phase, isDraft, title, blocks[{id, kind, src, changed?, removed?}], markdown, hearing, words, updating, note, maxMs, warnMs}` |
| `draftChunk` | `{id, seq, audio: base64 ≤ 4 MB, mime, elapsedMs, since}` → the view as soon as the chunk is recognised (`hearing`: words not yet drafted). Each `seq` is heard once, in order: a number already heard is skipped (a retry after a lost reply), a number past the next is refused (`a piece of the recording is missing`), and a piece whose recognition failed isn't counted, so its retry is heard |
| `draftState` | `{id, since, wait?}` → the view; with `wait`, held up to 20 s until something changes after `since` |
| `draftFinish` | `{id, seq?, audio? ≤ 20 MB, mime?, elapsedMs, since, draft?, check?}` → the view plus `raw`; `seq` is the next unused number, so a retried finish hears its audio once; `isDraft: false` means a prompt after all (the phone distils `raw`); otherwise the last update and the check against the whole transcript |
| `draftEdit` | `{id, since, markdown?, audio? ≤ 20 MB, mime?}` → the view: typed Markdown (never glows; blocks whose text is unchanged keep their ids, and `markdown` comes back exactly as typed until the next change by voice), then a change by voice (glows) |
| `draftClose` | `{id, how: sent\|kept\|discard}` → `{ok, transcriptKept}`: kept as text leaves the transcript on disk (7 days) |
| `distill` | `{raw, draft?}` → `{raw, text, editor, unclear[], by}` |
| `brief` | `{mode}` → `{speech, more[], report, by}`: spoken brief of the latest run plus the report for follow-ups |
| `details` | `{topic, mode}` → `{speech}` |
| `voiceStatus` | `{}` → `{speech, status, elapsedMs, tools, prompts}` |
| `voiceSession` | `{sdp, mode, persona?}` → `{sdp, model, provider}`: realtime call set up with the voice-layer config |
| `voices` | `{}` → `{personas: [{id, name, blurb, rate, phone}], sample}`: the voice picker; `sample` says whether the computer can play one |
| `speak` | `{text, persona?}` → `{audio: base64, mime}` from `voice.ttsUrl` or OpenAI TTS; `tts unavailable` means the phone speaks itself |
| `voiceState` | `{on, mode}` → `{ok}`: the agent is told its user is listening (expires after 150 s without a refresh) |

A phone draft never loses what was said (`DraftUplink` in `web/voice-core.js`, `phone-drafts.ts`; tested together in `test/voice-core.test.ts`). The phone keeps its whole recording until the draft is done; that recording is the fallback.

- **Numbered pieces.** Each chunk gets its number when it is cut and is sent on its own, after the ones before it. A piece whose request failed is retried by itself, never merged with newer audio, so a lost reply can't make the computer skip anything new. Finishing first sends the waiting pieces (each tried up to three times), then the rest under the next unused number.
- **No drafts here.** An older pi-mobile (`unknown request`), or three failures in a row before the draft shows, turns chunking off: the pieces and frames are dropped and the recording is an ordinary dictation.
- **The computer lost the draft** (pi restarted or shut down, idle for 30 minutes, more than four drafts open): the sheet says so, and ✓ transcribes the whole recording the phone still holds as an ordinary dictation, with a note saying why. ✕ while it forms does the same, into the message box.
- **Shutdown.** pi's `session_shutdown` drops every phone draft (`PhoneDrafts.dispose`, safe to call twice): model calls in flight are cancelled (also from a model that ignores the cancel), waiting `draftState` requests answer at once, and later requests find no draft, so the phone falls back as above. Transcripts stay on disk.
- **Sessions.** The draft's requests go to the session it was started from (its computer has the transcript). The sheet is the composer, which is shared by all sessions, so it stays when you switch; Send sends to the session on screen, with the images attached in the composer, like any message. Keep as text appends to whatever is in the message box now.
- **Size.** A draft's last piece and a `transcribe` recording are at most 20 MB; base64 in the request and the sealed, base64url'd body make that about 35.6 MB on the wire, under the hub's 40 MB request limit (`MAX_BODY`, `src/hub.ts`; `test/hub.test.ts` sends one through).

## Platform limits (verified against WebKit/Chromium sources, see research notes)

- Browsers give `getUserMedia` only to secure contexts: phones only ever load the HTTPS address, which `/remote` sets up with Tailscale Serve (on the computer, `http://127.0.0.1` is a secure context too).
- iOS stops capturing the mic when a Home Screen PWA goes to the background or locks; a Safari tab with an active capture keeps it longer. Voice mode keeps the screen awake (Wake Lock) and tells you when iOS took the mic away. Android Chrome exempts audible pages from freezing; verify on the device before relying on it.
- CarPlay has no path for web apps; the phone's audio plays through the car as usual.
- **The iPhone app** (`native/ios`, plan `plans/native-apps.md`) keeps the web UI in a web view and runs voice mode natively, through the same `voice-core.js` decisions, pairing and bridge requests. What it changes, all checked in the simulator only and **not yet verified on a device** (`native/ios/README.md` → Device checklist):
  - A background audio session keeps the mic with the screen locked (phone in a pocket). [device]
  - Apple's voice-processing I/O gives echo cancellation for speakerphone barge-in. [device]
  - The app reaches computers over HTTPS only (`native/ios/README.md` → ATS), like the web's voice mode; it records natively, so dictation and voice mode need no browser permission. Basic voice and dictation pass in the simulator; realtime voice over WebRTC needs a computer with it set up. [device]
  - Before the first voice mode or dictation, the app asks once whether your voice may go to OpenAI and your computer (`native/ios/README.md` → Consent).
  - The Action button, Control Center and Siri ("Talk to pi in pi") start a conversation; a Live Activity shows the state and question on the lock screen and Dynamic Island, with Mute and End. Starting while locked may still open the app. [device]
  - AirPods press-to-mute goes through iOS's input mute, without CallKit; unverified. [device]
  - Notifications come through Apple's push service (needs a paid Apple developer account), with the text sealed so Apple sees only "pi". [device]
  - CarPlay: no UI; the Live Activity appears there by itself. A CarPlay app would need an Apple entitlement.
- The ChatGPT-sign-in realtime endpoint is the one Codex uses; it is undocumented and may change. With `OPENAI_API_KEY` set, the official `api.openai.com/v1/realtime/calls` endpoint is used instead. Without either, voice mode runs the cascaded pipeline (host STT + spoken brief + the phone's own speech synthesis).

### Other projects looked at

[Voicebox](https://github.com/jamiepine/voicebox) (local voice studio: TTS engines with cloning, Whisper dictation with LLM cleanup, an OpenAI-compatible `/v1/audio/speech`). It has no VAD, barge-in or true streaming, so nothing for the realtime path. Taken from it: collapsing recogniser repetition loops before distillation, the spoken-path rule ("src slash components" → `src/components`), and the OpenAI-compatible speech endpoint as an optional voice for basic mode (`voice.ttsUrl`), so Voicebox or Kokoro can speak on the phone. Left out: its batch Whisper STT (on-device SpeechAnalyzer and realtime transcription are better here), cloning, and speaking on the host's speakers.
